# llm-router — Go rewrite design

Date: 2026-09-21
Status: approved, not yet implemented

## Goal

Replace the Node implementation of jev-router with a single Go binary that:

1. keeps every feature the Node version has today — Claude Code routing, Codex
   routing, the explanation report, and the status line;
2. fixes the prompt-cache loss that happens when the router changes models
   mid-conversation;
3. installs with `brew install djalmaaraujo/tap/llm-router` and needs no Node,
   no npm, and no runtime at all.

## Why a rewrite, stated honestly

A native binary does **not** make routing faster. Measured on this machine:

| Cost | Value | How often |
| --- | --- | --- |
| Node startup | 25-50 ms | once per session |
| Jev call | 300-350 ms warm, ~900 ms cold | once per turn |
| Anthropic response | seconds | every turn |

Routing latency is network latency. A proxy is IO-bound. Go over Rust, or Go
over Node, changes nothing a user can feel in a turn.

The real wins are these:

- **No runtime dependency.** One file. `brew install`, done.
- **The status line stops spawning Node.** Claude Code renders the status line
  often, and each render is a fresh `node` process today (~25 ms). As a
  subcommand of the same binary it costs ~3 ms.
- **The release pipeline already exists.** `djalmaaraujo/piper` is Go, released
  with GoReleaser, and its cask in `djalmaaraujo/homebrew-tap` is generated by
  that release. The same pipeline serves this project with no new machinery.

Go, not Rust, for that last reason. Rust would give a smaller binary and lower
memory and would need a new release pipeline to get there. Neither matters for
an IO-bound proxy.

## Non-goals

- Windows. The Node version carries `.cmd` shim handling, `PATHEXT` lookup, and
  shell quoting for it. We drop all of that and ship macOS and Linux, which is
  what the Homebrew cask serves and what can actually be tested here.
- A second routing provider. The `Router` interface exists so one can be added
  without touching the policy, but only Jev is implemented.
- Changing what Jev is asked. The questions, the rubric, and the scoring stay
  exactly as the Node version has them.

## Commands

GoReleaser builds one binary, `llm-router`. The cask installs it and creates
three symlinks. Dispatch reads `argv[0]` and falls back to a subcommand.

| Command | Same as | Does |
| --- | --- | --- |
| `llmr-claude` | `llm-router claude` | runs Claude Code with routing |
| `llmr-codex` | `llm-router codex` | runs Codex with routing |
| `llmr-explain` | `llm-router explain` | prints the last routing decision |
| — | `llm-router statusline` | renders the status line; internal |

The bundled skill is `/llmr-explain`, and it shells out to `llm-router explain`
instead of to `node`.

## Layout

```
llm-router/
  main.go                     argv[0] dispatch and subcommands
  internal/
    config/                   tiers, prices, thresholds, env loading
    cost/                     the cache math; pure
    policy/                   Decide(); pure
    router/                   Router interface
    router/jev/               POST /v1/systemone
    proxy/                    shared plumbing: listener, upstream, SSE tap
    proxy/claude/             /v1/messages rewrite, schema sanitize, usage tap
    proxy/codex/              Responses API rewrite, provider injection
    state/                    per-session decisions under the temp dir
    explain/                  the report
    statusline/               the status line
    launch/                   PATH lookup, env assembly, spawn, settings restore
  skills/llmr-explain/SKILL.md
  .goreleaser.yaml
  .github/workflows/ci.yml
  .github/workflows/release.yml
```

`cost` and `policy` hold every decision and touch no IO. They are the parts
worth testing hardest, and they can be tested without a network or a process.

## The routing provider

One HTTP call, reimplemented with the standard library. No SDK exists for Go and
none is needed.

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <key>
Content-Type: application/json

{ "state": {...}, "questions": {...}, "model": "jev-latest" }
```

The response is `{ "model": ..., "answers": {...}, "usage": {...} }`. Answers
come back keyed by question name. A `choice` answer carries `choice`,
`confidence`, and `probabilities`; a `score` answer carries `score`,
`confidence`, `legend`, and `probabilities`.

Timeouts stay where the Node version pinned them, for the same reason: this sits
on the hot path of every turn.

| Setting | Value |
| --- | --- |
| Per-attempt timeout | 1500 ms |
| Whole-call deadline | 3000 ms |
| Retries | 1 |

Routing is fail-open. Any error, timeout, or unparseable answer means "keep the
current model", never "block the prompt".

The `Router` interface:

```go
type Decision struct {
    Choice        string
    Confidence    float64
    Metrics       Metrics
    Request       any
    Response      any
    Elapsed       time.Duration
}

type Router interface {
    Route(ctx context.Context, in Input) (*Decision, error)
}
```

`router/jev` is the only implementation.

## The cache fix

### What is broken today

Anthropic's prompt cache is keyed on the model. Changing models mid-conversation
invalidates it, and the next turn re-pays cache creation for the whole
conversation prefix instead of a cache read. Claude Code uses the 1-hour TTL,
so a rebuild costs **2x** base input, not 1.25x.

The Node version guards this with one static rule: refuse a downgrade once the
conversation passes 20 000 tokens. That rule is wrong in three ways.

1. It only guards downgrades. An upgrade at 150 000 tokens burns the same cache
   and costs more to rebuild.
2. The threshold is a guess, not a cost. Doing the arithmetic shows 20 000 is
   far too strict — it blocks downgrades that would save money.
3. The token count feeding it is itself a guess:
   `JSON.stringify(body.messages).length / 4`.

### Prices

Base rates per million tokens, and the cache multipliers that apply to them.

| Tier | Input | Output | Cache read | Cache write, 1h TTL |
| --- | --- | --- | --- | --- |
| haiku 4.5 | $1.00 | $5.00 | 0.1x | 2x |
| sonnet 5 | $2.00 | $10.00 | 0.1x | 2x |
| opus 5 | $5.00 | $25.00 | 0.1x | 2x |
| fable 5.1 | $10.00 | $50.00 | **0.025x** | 2x |

Fable reads at $0.25 per million, which is 0.025x rather than 0.1x. It gets its
own multiplier in the table; it is not an exception in the code.

### The rule

`cost.SwitchPaysOff` compares staying against switching over a horizon of turns.

```
stay   = horizon * (cached * read(from) + out * outRate(from))
switch = cached * write(to) + out * outRate(to)
       + (horizon-1) * (cached * read(to) + out * outRate(to))

switch when switch < stay
```

Worked example, 80 000 cached tokens, 2 000 output tokens, opus to haiku:

- staying costs `0.08 * $0.50 = $0.04` of input per turn, plus `$0.05` of output
- switching costs `0.08 * $2.00 = $0.16` once, then `$0.008` and `$0.01` per turn
- the switch pays for itself in **2.1 turns**

The Node rule blocks that switch at anything past 20 000 tokens. It should not.

### Why a token threshold cannot work

Break-even turns, at 2 000 output tokens per turn:

| From -> to | 80k cached | 100k cached | 500k cached |
| --- | --- | --- | --- |
| opus -> haiku | 2.1 | 2.4 | 4.0 |
| opus -> sonnet | 5.6 | 6.3 | 10.6 |
| sonnet -> haiku | 8.4 | 9.5 | 15.8 |

Read down a column, not across a row. **Which pair of tiers is involved matters
more than how big the conversation is.** Dropping opus to haiku pays off in two
to four turns at every size in that table. Dropping sonnet to haiku needs eight
to sixteen, because sonnet's cache reads are already cheap, so there is little
left to save and the rebuild still costs full price.

One number keyed on context size cannot express that, at any value. This is the
structural reason the Node rule is wrong, not just mis-tuned.

### The horizon

`horizon` is how many more turns this conversation will keep using the same
cached prefix. Nobody knows that number in advance.

A short horizon under-switches, which keeps the cache. A long horizon
over-switches, which burns it. The failure modes are not symmetric, so the
default is deliberately short: **5 turns for a main conversation, 2 for a
sub-agent**, tunable with `LLMR_SWITCH_HORIZON`.

At horizon 5 the table above allows opus to haiku at every size, and holds the
other two pairs. That is the intended behaviour.

### Upgrades are not blocked on cost

An upgrade is a capability decision, not a cost decision. Refusing haiku to opus
to protect the cache makes the turn fail, and a failed turn plus a retry costs
more than the rebuild it avoided.

So: **the cost rule applies to downgrades only.** The one brake on the upgrade
side is confidence — past `bigContextTokens`, an upgrade needs Jev confidence
above `bigContextMinConfidence`, because sonnet to opus at 500 000 tokens spends
$2.00 in a single request and a coin-flip answer should not spend it.

### Real numbers instead of an estimate

The proxy already sits on the response stream. It reads usage from there.

- `message_start` carries `usage` with `input_tokens`,
  `cache_read_input_tokens`, and `cache_creation_input_tokens`. Their sum is the
  prefix that will be cached for the next turn.
- The final `message_delta` carries `output_tokens`.

The tap scans incoming chunks only until it finds `message_start`, and keeps a
rolling 2 KB tail to read `output_tokens` on end. It never buffers the body and
never delays a byte reaching the client.

### Sub-agents

Claude Code runs sub-agents through the same endpoint. The conversation key
already separates them, but the policy treats them identically today.

A sub-agent starts with a fresh, small cache, so switching its model costs
almost nothing. The main conversation is the one holding 100 000+ tokens.

The first routed conversation key seen for a session is the main conversation.
Any new key under that session afterwards is a sub-agent. Sub-agents route with
a short horizon and no downgrade brake; the main conversation gets the full
arithmetic.

This is the workable form of the sub-agent idea raised on the upstream issue: a
proxy cannot make Claude Code spawn a sub-agent, but it can stop treating a
sub-agent's cheap, disposable context like the main conversation's expensive one.

### What `explain` shows

`cache rebuild avoided` explains nothing. The report shows the arithmetic:

```
Decision: held on SONNET
  rebuild on HAIKU   $0.190 once
  saving             $0.020 per turn
  pays off in        9.5 turns, horizon is 5
```

## Porting traps

These are rules for the implementation, not reminders.

**1. Decode with `UseNumber`.** The proxy mutates an undocumented body and must
return everything else untouched. A plain `map[string]any` decode turns every
number into `float64`, and `max_tokens: 1000000` goes back on the wire as
`1e+06`. Every decode of a request or response body uses
`json.Decoder` with `UseNumber()` set. This is the trap that silently corrupts
requests.

**2. Go sorts map keys on marshal.** Node preserves insertion order. The API
does not care, and Anthropic computes the cache after parsing, over
`tools` -> `system` -> `messages`. The risk is low but it is not zero, and it is
verified by a round-trip test over recorded real bodies rather than assumed.

**3. Parse the whole body in v1.** A tool-loop continuation only needs `model`
rewritten, and parsing 500 KB to change one field is waste. Targeted byte
replacement is the obvious optimisation and it is wrong: `"model":"llm-router"`
can appear inside message text and corrupt the body. v1 parses. Optimise only if
a profile shows it matters.

## Compatibility

Existing environment variables keep working, so the key already in
`~/.jev-router.env` needs no change.

| Purpose | Accepted |
| --- | --- |
| API key | `LLMR_API_KEY`, `JEV_API_KEY`, `TYPESAFE_API_KEY` |
| Env files, in order | `./.env`, `~/.llm-router.env`, `~/.jev-router.env`, `~/.jev-claude.env` |

Every `JEV_*` flag the Node version reads keeps working under both its old name
and an `LLMR_*` alias: debug, dump, no-statusline, allow-fable, and the four
Codex model overrides.

The sentinel model id Claude Code sends stays `jev-router`. It is a wire value
that the proxy matches exactly; renaming it buys nothing and breaks a session
resumed from the Node version.

## Testing, which gates the release

No release happens until all four levels pass. This is the order they run in.

**1. Unit, pure packages.** `cost` and `policy` carry the money decisions and
have no IO. Table tests over the worked examples in this document: every cell of
the break-even table, the fable read rate, the two horizons, override detection,
unavailable-tier substitution, and the confidence rules. The break-even table is
the test fixture — if the code and the table ever disagree, one of them is a bug
and the test says which.

**2. Wire parity against the Node version.** The Node version dumps real request
bodies with `JEV_DUMP`. We record a corpus with it — first turn, tool-loop
continuation, sub-agent turn, a body with MCP schemas needing sanitising, a
Haiku-bound body carrying `thinking` and `context_management`, and a Codex
Responses body — then assert the Go proxy produces byte-identical output to the
Node proxy for each. This is what proves the port, and it runs in CI.

**3. Live, both CLIs.** `llmr-claude` and `llmr-codex` against the real
services, with `LLMR_DEBUG=1`:
- routing happens, and the log reports the model the API says served the turn;
- context tokens in the log match `/context` in Claude Code, which is the check
  that the usage tap reads the right numbers;
- a conversation grown past 50 000 tokens keeps its cache — `cache_read` stays
  high across turns and no unexplained `cache_creation` appears;
- a sub-agent routes independently and does not move the main tier;
- killing the Jev endpoint mid-session degrades to "keep current model" and
  never blocks a prompt;
- `/model` picking a real model pauses routing, and picking Jev Router resumes;
- exiting restores the previously saved default model.

**4. Install rehearsal.** Build the cask locally and install from a local tap on
a clean `PATH` with no Node present. All three commands work, `/llmr-explain`
works inside Claude Code, and `brew uninstall` leaves nothing behind.

Only then does a tag get pushed.

## Release

`.goreleaser.yaml` follows `djalmaaraujo/piper`: darwin and linux, amd64 and
arm64, and a cask published to `djalmaaraujo/homebrew-tap` with the quarantine
attribute stripped in `postflight`.

CI runs `go test ./...`, `go vet ./...`, and `gofmt -l`. The release workflow
fires on a tag and is the only thing that publishes.

The first tag is cut by hand, after level 4 passes.
